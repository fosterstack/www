My build cache server won't start. What does the error mean?

If FosterStack Cache exits right after you start it, read the last line of its log. In our runs every startup failure ended with one fscache: fatal line and exit code 1, and the line named the cause.

The short answer

  • A rejected setting stops the server before it touches the data folder. The line names the variable and the value. Sizes must be whole numbers of bytes, so 10GB is refused.
  • A problem with the address or the data folder stops it a moment later. A busy port, a folder it cannot write to and a data path that is a file each gave a clear line. In a container we reproduced the folder case with a data volume that belonged to root: see permission denied on the data folder.
  • A second server on the same data folder waits about 5 seconds, then exits. It ends with the same fatal line and code 1. The first one kept serving.
  • Some mistakes do not stop the server. A misspelled setting name was ignored without a warning, and an emptied index file was accepted without a warning, so lost entries go unnoticed.

Find your error

The first column is what we saw in the log. The other two columns are our advice, not a test result. DIR stands for a folder on our test machine and PORT for the port we used.

Build cache server exits with "permission denied" on its data

You start the container and it stops straight away. The log ends with permission denied. The cause we reproduced is who owns the data directory.

What you see

The container exits with status 1 within a few seconds, and its log says:

{"level":"ERROR","msg":"fscache: fatal","error":"write shutdown marker: open data/.unclean-shutdown: permission denied"}

Why it happens

The server does not run as root. It runs as user 65532, and it keeps its files in a data folder inside /home/nonroot. If that folder already exists and belongs to someone else, the server cannot write to it and stops.

We reproduced it with a volume that already held data owned by root, which is what you get after restoring a backup as root:

/d       0:0   drwxr-xr-x      (owner:group, mode)
/d/data  0:0   drwxr-xr-x

The fix

Give the whole tree to user 65532. The image has no shell, so use a throwaway container to do it:

docker run --rm -v fscache-data:/d ubuntu:24.04 chown -R 65532:65532 /d

In our runs, after that the same image started normally: /healthz answered ok and an upload returned 201.

What does not cause it

  • A new, empty named volume. This is what our first-run steps create, and the volume then belongs to 65532. We also tried a new empty volume whose top folder we had set to root. The server still started, and afterwards the folder belonged to 65532, because Docker copies the image's ownership into an empty volume the first time it is used.

When the server starts, but not the way you meant

  • A misspelled setting name was ignored. With FSCACHE_MAXBYTES=1500 the server started with no warning, and its start line said "max_bytes":0. Four uploads of 1,000 bytes were all stored. With FSCACHE_MAX_BYTES=1500, one entry was left and 3 were evicted.
  • An emptied or deleted meta.db was not an error. The server started and still served an old entry. But /statusz counted only the entry we stored afterwards: 1 entry and 100 bytes, not 4 entries.
  • A bad address still left a data folder behind. The server created meta.db and blobs before it failed to listen. A rejected setting did not create any folder.
  • An HTTPS address does not work. The docs say the server speaks plain HTTP and has no certificate handling, so TLS goes in front of it. curl with an https:// address to the server's own port failed with exit code 35, and the server logged nothing. See production build cache with Docker Compose, nginx and TLS.

What to do

Our advice, not a test result:

  • Read the last line first. It names the variable, the value or the path.
  • After every change, read the fscache: starting line. It prints the address, the data folder, the size cap and whether logins are on. A misspelled name shows up there as a setting that did not change.
  • Write sizes in bytes. 10GB will stop the server, which is better than a silent default.
  • Start the server as the user that owns the data folder. In a container, that means giving the data volume to the user the image runs as, 65532 in our runs. The command is in the permission-denied section above. If you restore a backup into the volume, the restore has to keep that ownership.
  • Keep one server per data folder. A start on a full disk is on what happens when the disk fills up.

How we checked

FosterStack Cache 0.2.1 on a Mac (arm64). The permission-denied cases used the 0.2.1 container image. Each non-container case was one start with a clean environment that held only the address, the data folder and the setting under test, watched for 3 seconds with a check every quarter of a second. Every failed start exited with code 1. The non-container ones took under a second, except the shared folder. The container cases exited within a few seconds. A server we stopped with a normal stop exited with code 0.

The log is one JSON line per event. A start that got as far as listening printed fscache: starting first. A rejected setting or a data folder problem printed only the fatal line. We caused one mistake at a time, so we do not know which line shows first when two settings are wrong.

Not tested: container starts other than the permission-denied cases above, a bind mount of a host folder on Linux (the same rule should apply, as the folder has to be writable by 65532, but we ran on a Mac), Kubernetes without the fsGroup setting (the manifests on our Kubernetes page set fsGroup: 65532, and we ran them with it), running the container as root (it is not what we document), Linux, Windows, IPv6 addresses, a data folder on a network disk, and a Gradle build against an HTTPS address that the server does not speak.

We ran this page again on a GitHub-hosted Linux machine with FosterStack Cache 0.2.2 and the 0.2.2 container image. Every start failure in the table printed the line shown and exited with code 1, and that line was the last line of the log. A second server on a held data folder gave up after 5.0 seconds. Every setting that the page says is accepted or ignored behaved as written. The container on a volume owned by root exited with status 1, and after the chown command it started. The run and its log are public.
