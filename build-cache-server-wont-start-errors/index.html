My build cache server won't start. What does the error mean?

If FosterStack Cache exits right after you start it, read the last line of its log. In our runs every startup failure ended with one fscache: fatal line and exit code 1, and the line named the cause.

The short answer

  • A rejected setting stops the server before it touches the data folder. The line names the variable and the value. Sizes must be whole numbers of bytes, so 10GB is refused.
  • A problem with the address or the data folder stops it a moment later. A busy port, a folder it cannot write to and a data path that is a file each gave a clear line.
  • A second server on the same data folder waits about 5 seconds, then exits. It ends with the same fatal line and code 1. The first one kept serving.
  • Some mistakes do not stop the server. A misspelled setting name was ignored without a warning, and an emptied index file was accepted without a warning, so lost entries go unnoticed.

Find your error

The first column is what we saw in the log. The other two columns are our advice, not a test result. DIR stands for a folder on our test machine and PORT for the port we used.

When the server starts, but not the way you meant

  • A misspelled setting name was ignored. With FSCACHE_MAXBYTES=1500 the server started with no warning, and its start line said "max_bytes":0. Four uploads of 1,000 bytes were all stored. With FSCACHE_MAX_BYTES=1500, one entry was left and 3 were evicted.
  • An emptied or deleted meta.db was not an error. The server started and still served an old entry. But /statusz counted only the entry we stored afterwards: 1 entry and 100 bytes, not 4 entries.
  • A bad address still left a data folder behind. The server created meta.db and blobs before it failed to listen. A rejected setting did not create any folder.
  • An HTTPS address does not work. The docs say the server speaks plain HTTP and has no certificate handling, so TLS goes in front of it. curl with an https:// address to the server's own port failed with exit code 35, and the server logged nothing. See production build cache with Docker Compose, nginx and TLS.

What to do

Our advice, not a test result:

  • Read the last line first. It names the variable, the value or the path.
  • After every change, read the fscache: starting line. It prints the address, the data folder, the size cap and whether logins are on. A misspelled name shows up there as a setting that did not change.
  • Write sizes in bytes. 10GB will stop the server, which is better than a silent default.
  • Start the server as the user that owns the data folder.
  • Keep one server per data folder. A start on a full disk is on what happens when the disk fills up.

How we checked

FosterStack Cache 0.2.1 on a Mac (arm64). Each case was one start with a clean environment that held only the address, the data folder and the setting under test, watched for 3 seconds with a check every quarter of a second. Every failed start exited with code 1, and all of them in under a second except the shared folder. A server we stopped with a normal stop exited with code 0.

The log is one JSON line per event. A start that got as far as listening printed fscache: starting first. A rejected setting or a data folder problem printed only the fatal line. We caused one mistake at a time, so we do not know which line shows first when two settings are wrong.

Not tested: Docker or Kubernetes starts, Linux, Windows, IPv6 addresses, a data folder on a network disk, and a Gradle build against an HTTPS address that the server does not speak.
