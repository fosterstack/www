How FosterStack Cache is built and signed

You are about to run our software inside your build pipeline. How do you know the files you run are the ones we built? Every release is signed and checked at every step, and you can verify it yourself. This page says how.

We do it to our own pipeline first

FosterStack's business is helping organisations secure their build and release pipeline. We started with a build cache your team can know is secure, and we secure our own release pipeline the same way before we ask you to trust it. [TO-VERIFY: pipeline: the v0.3 chain, secured before the product ships]

Releases are built only in CI

No release file is ever made on a person's laptop, ours included. A release starts when a signed tag is pushed, and there is no manual release path. That is what makes the signatures mean something: nobody can forge a release that GitHub's own build machines never built. [TO-VERIFY: pipeline: no manual release path in v0.3]

The steps a release goes through

Signed at every stage, verified together at release. Each stage signs its own statement about the exact files, and no stage takes the one before it on trust. [TO-VERIFY: pipeline: each v0.3 stage signs its own statement; the Release stage verifies all together]

  1. Source check. The tag and the commit must be signed by an allowed signer, sit on the main branch, and have every required check green. [TO-VERIFY: pipeline: v0.3 source admission unchanged from v0.2.2]
  2. Build. The binaries and the image's packages are built once. The image is assembled from those signed packages, with no base image. [TO-VERIFY: cache: melange packages, apko image, no base image]
  3. Sign. A separate stage, with its own identity, records the build and signs it. [TO-VERIFY: pipeline: the Sign boundary stage and its own identity]
  4. Rebuild. The release is built again, independently. The results must be identical, or the release fails. [TO-VERIFY: pipeline: the Rebuild stage]
  5. Check. Every scanner on our list runs against the exact images. A finding blocks the release unless a published VEX statement explains why it does not apply. The Gradle and Maven acceptance tests run against the same images. [TO-VERIFY: pipeline: scanner list and acceptance suites at v0.3]
  6. Release. One step verifies every earlier signature together. Anything missing stops the release. Then the same digests are published, promoted without a rebuild, and checked again the way a customer would check them. [TO-VERIFY: pipeline: the Release stage]

The full description, as the pipeline actually runs, is in RELEASING.md. [TO-VERIFY: pipeline: RELEASING.md matches the v0.3 chain]

What you get with each release

  • Container images on GitHub's registry, signed without a stored key (Sigstore), with build provenance. [TO-VERIFY: pipeline/cache: v0.3 image signing and provenance]
  • Plain binaries and a checksums.txt with its own signature file. [TO-VERIFY: cache fix A #276: which files the signed checksums list covers]
  • A software bill of materials (SBOM) for each binary archive.
  • A VEX file saying which known vulnerabilities do and do not affect the release.
  • A release-manifest.json listing every file and its digest. [TO-VERIFY: cache: manifest layout at v0.3]

All of it is public. You do not need an account or a purchase to check any of it. The commands are on verify a release yourself.

Kept patched

The current release's images are scanned again every day, so a vulnerability disclosed against something we already shipped raises an issue without anyone having to remember to look. [TO-VERIFY: cache/ops: the daily rescan, and automatic patch releases not yet cut]

What we do not claim

  • Vulnerable dependencies fixed fast: our target is 48 hours from disclosure (the scope is in SECURITY.md).
  • A signature shows who signed these exact files. It does not show the software has no bugs.
  • The paid tiers are not built. Everything here is the free MIT core.
