Verify a FosterStack Cache release yourself

You should not have to take our word for what you run. These steps check the image signatures, the signed file lists, the digest, how the release was built and its parts list, using only cosign, gh, curl, jq and sha256sum. They are for v0.3.0 and later. For v0.2.x, use the image verification guide, but set VER to your version (for example VER=0.2.2) instead of running its first command.

You need no account to pull the images or to run cosign. Downloading release files with gh needs gh auth login; you can also download them from the release page in a browser.

Set the version

VER=0.3.0
echo "$VER"

Set VER to the release you run, v0.3.0 or later.

There are two images, production and -fips.

1. The key, then the signature and who signed it

Every release key is signed by one root key. Check the key before you trust a signature made with it. Fetch the root key from the repository at the release tag, and download the key manifest and its signature from the release page:

curl -fsSL -o release-key-root.pub "https://raw.githubusercontent.com/fosterstack/cache/v${VER}/.github/policy/release-key-root.pub"
gh release download v${VER} --repo fosterstack/cache \
  -p release-key-manifest.json -p release-key-manifest.sig
cosign verify-blob --key release-key-root.pub --signature release-key-manifest.sig --insecure-ignore-tlog release-key-manifest.json
jq -r .public_key release-key-manifest.json > release.rsa.pub

Run the last command only if the one before it prints Verified OK. It writes the release key, release.rsa.pub, from the manifest. The check skips the log because the root key is kept offline, so its signature has no log entry.

Check valid_from and valid_to in the manifest against the current time. Stop if the current time is at or after valid_to (valid_to is optional) or before valid_from, whatever the release's publish date.

The newest manifest and its signature for the same key_id are among the release assets. Download them into a separate folder (with no tag, gh takes the newest release) and verify them the same way as the first, including the dates above:

mkdir -p newest
gh release download --repo fosterstack/cache --dir newest \
  -p release-key-manifest.json -p release-key-manifest.sig
cosign verify-blob --key release-key-root.pub --signature newest/release-key-manifest.sig --insecure-ignore-tlog newest/release-key-manifest.json
jq '{key_id, valid_from, valid_to, revoked_at}' release-key-manifest.json newest/release-key-manifest.json

Stop if the two key_id values differ. Stop if the newest manifest has a revoked_at that is at or before the current time.

Now check the images:

cosign verify --key release.rsa.pub ghcr.io/fosterstack/cache:${VER}
cosign verify --key release.rsa.pub ghcr.io/fosterstack/cache:${VER}-fips

This shows that our release key signed these exact images. The key is held in a cloud key service; only the signing jobs and the release job can use it, and no job that builds can sign. The release job signs the images; the signing jobs sign the records and the provenance. Each signature is recorded in Rekor, the public transparency log. Every command below uses the same release.rsa.pub.

2. The file lists are ours, and your files match them

gh release download v${VER} --repo fosterstack/cache \
  -p checksums.txt -p checksums.txt.bundle \
  -p release-files.sha256 -p release-files.sha256.bundle \
  -p release-manifest.json -p "fscache_${VER}_linux_amd64.tar.gz"
for f in checksums.txt release-files.sha256; do
  cosign verify-blob --key release.rsa.pub --bundle "$f.bundle" "$f"
done
sha256sum -c <(grep "fscache_${VER}_linux_amd64.tar.gz" checksums.txt | grep -v sbom)
sha256sum -c <(grep release-manifest.json release-files.sha256)

Do the signature check first. Without it, a list only proves that your files match a file anyone could have written. The archives are covered by the signed checksums.txt, and the manifest by the signed release-files.sha256.

3. The digest is the one in the release

jq -r '.images[] | "\(.variant) \(.digest)"' release-manifest.json

Every statement names an image by digest, never by tag. The digest you pulled should be in this list.

4. How it was built

This step and the next have not yet been run against a published v0.3.0 release. If a command fails, write to hello@fosterstack.com.

gh release download v${VER} --repo fosterstack/cache \
  -p provenance.bundle.json
cosign verify-blob-attestation --key release.rsa.pub --bundle provenance.bundle.json \
  --type https://slsa.dev/provenance/v1 --check-claims=false
jq -r '.dsseEnvelope.payload | @base64d | fromjson | .subject[] | .name + " sha256:" + .digest.sha256' provenance.bundle.json
# the digest of the production image you pulled (for example from docker images --digests):
DIGEST=sha256:...
jq -e --arg d "${DIGEST#sha256:}" '.dsseEnvelope.payload | @base64d | fromjson | any(.subject[]; .name == "image-production" and .digest.sha256 == $d)' provenance.bundle.json

The SLSA provenance is signed in a separate job, stage-sign.yml. It takes the list of digests the build made, checks it against the build's signed record and runs no code from the build. The first jq lists each image it names, with its digest. The second prints true only if the provenance names the production image you pulled; for the -fips image use the name image-fips.

5. The parts list and what it was assembled from

gh release download v${VER} --repo fosterstack/cache \
  -p production.sbom.json -p production.sbom.json.bundle \
  -p production.full.lock.json -p production.full.lock.json.bundle
for f in production.sbom.json production.full.lock.json; do
  cosign verify-blob --key release.rsa.pub --bundle "$f.bundle" "$f"
done

The SBOM lists what is in the image. The lock file lists every package the image was assembled from, by checksum. Repeat with fips.sbom.json and fips.full.lock.json for the -fips image.

What this proves

  • A valid signature proves who signed these exact files, and that the signing was recorded publicly.
  • Provenance proves which workflow, at which tag, produced the digests it names.
  • It does not prove the software has no bugs. Scan results and our statements about findings are separate: see the security policy.

Each stage of the release also writes a record with Witness, an open-source build-record tool. The stages that build sign their record with a throwaway key; a signing job checks each record against the files it names and signs it with the release key. The records are attached to the release.
