Why did this one task miss the build cache?

Run the slow build twice with --info -Dorg.gradle.caching.debug=true and save each log. Compare the lines that start with Appending, and the line that differs names the input that changed.

Find the input, step by step

Our advice, with the commands we ran:

  1. Build once and save the log. Use the same tasks that missed. 
    gradle compileJava greetEnv --info -Dorg.gradle.caching.debug=true > run1.log
  2. Keep only the key lines. The full log is long. 
    grep -E '^(Appending|Build cache key for task)' run1.log > run1.keys
  3. Do the same for the build that missed. That is the other machine, the other folder or the build after your change. Save it as run2.keys.
  4. Compare. 
    diff run1.keys run2.keys
  5. Read the first line that differs. Each task writes its Appending lines, one per input, and then its Build cache key for task line. The input name is in quotes. In our runs a changed environment variable showed up like this: 
    < Appending input value fingerprint for 'label' to build cache key: 4c54da94...
> Appending input value fingerprint for 'label' to build cache key: 96dabe02...
< Build cache key for task ':greetEnv' is 3dd3b463...
> Build cache key for task ':greetEnv' is 2a408a1a...

Compare the hash after the colon. For file inputs the text in braces is only a display of the path, and it can change while the hash stays the same.

If the two key lines are identical, the key is not the problem. Look at the server instead, starting with Gradle remote build cache not working.

A rerun is not a miss

With --rerun-tasks every task ran, but the keys were identical to the previous build. The log says why, and the result is stored again:

Task ':greetStable' is not up-to-date because:
  Executed with '--rerun-tasks'.
Stored cache entry for task ':greetStable' with cache key f1bf5e9a...

A real miss has a new key and no such line. A hit prints FROM-CACHE and Loaded cache entry.

When a task has no key at all

Some tasks never look in the cache, so there is nothing to diff. Gradle says so with Caching disabled for task ... because:. In our runs the reasons were:

What we didReason Gradle printed
A condition that was false, outputs.cacheIf("only on CI") { false }'only on CI' not satisfied
outputs.doNotCacheIf("a developer asked for no caching") { true }'a developer asked for no caching' satisfied
A task class that is not marked cacheableCaching has not been enabled for the task
A task with actions and no declared outputsGradle would require more information to cache this task
Two tasks writing the same output fileFor the second one: Gradle does not know how file 'build/overlap.txt' was created, followed by a note that cached outputs need exclusive paths. The first task was cached

None of these tasks printed a Build cache key line.

How we checked

FosterStack Cache 0.2.1 on a Mac (arm64), no password. Gradle 9.8.0, --no-daemon, a new Gradle home for every build, the local build cache off. Java 21 for every build except the Java 27 row, which used Homebrew OpenJDK 27 for the Gradle run. The test project had one Java class and five small cacheable tasks. Each row is one run, we did not repeat them, and we report counts and log lines, not times.

Not tested: other Gradle versions, Maven, Kotlin or Android builds, a second machine, and inputs that come from dependencies. Related: Gradle build cache hit rate low and why did my whole build rerun after a small change.
