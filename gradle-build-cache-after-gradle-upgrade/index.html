Why your Gradle build cache goes cold after a Gradle upgrade

Know before you upgrade: in our runs a Gradle version restored only the cache entries it had built itself, so the first builds on a new version rebuilt instead of restoring. At FosterStack we prove everything, so here is how we proved it to ourselves: three series of real builds across Gradle 9.5.1, 9.7.1 and 9.8.0, and the cache-key inputs that differ.

The short answer

  • Gradle 9.8.0 and 9.7.1 did not restore each other's compile results, in either direction. 9.8.0 did not restore 9.5.1's either (9.5.1 first only). That is one build per case.
  • Each version restored its own earlier entry when we went back to it.
  • The cache key differed. The values that come from your project were identical; the lines that differ describe Gradle's own task and compiler objects.

What we ran

The four-module project from Gradle build cache for a monorepo, and its :core:compileJava task, against a self-hosted cache (FosterStack Cache 0.2.1). We used Gradle 9.8.0 (installed with Homebrew), and Gradle 9.7.1 and 9.5.1 from the official downloads, The two downloaded files were each checked against the SHA-256 checksum we fetched with them. All three ran on the same Java, Temurin 21.0.12.1, so only Gradle differed.

There were three series of three builds. Each series started on a new, empty cache server. Every build used a fresh copy of the project with no earlier build output, a new empty Gradle home, and the local build cache off. All builds ran on the same Mac. Two earlier attempts at the script had bugs and ran no builds; the table is from the third run. Each cell below is one build, and every build ended with BUILD SUCCESSFUL.

SeriesBuild 1Build 2 (other Gradle)Build 3 (first Gradle again)
9.8.0 first, then 9.7.19.8.0: ran9.7.1: ran9.8.0: FROM-CACHE
9.7.1 first, then 9.8.09.7.1: ran9.8.0: ran9.7.1: FROM-CACHE
9.5.1 first, then 9.8.09.5.1: ran9.8.0: ran9.5.1: FROM-CACHE

"Ran" means Gradle printed :core:compileJava with nothing after it. So the second Gradle version found nothing it could use, and the first version found its own entry again.

What differs in the cache key

Gradle can print every input it puts into a task's cache key. In two extra builds, one under Gradle 9.8.0 and one under 9.7.1, with no cache server running (the key is worked out before the cache is contacted), we used this option and compared the lines for :core:compileJava:

gradle :core:compileJava -Dorg.gradle.caching.debug=true

The cache keys came out different (0850668412069d9ad6250e00d6fa0d31 for 9.8.0 and b644334977a3e4eb2455429377dc58b9 for 9.7.1). The debug output listed 39 input lines for each key. Here is what we found:

  • The same in both: the fingerprint of the project's source files (f3429a2c9b16b51bf45944cd89e7ed46), the compiler arguments, the release setting, the encoding, the debug and fork on/off flags, the classpath (empty here) and the output names.
  • Different (11 of the 39 lines): the task's own implementation (org.gradle.api.tasks.compile.JavaCompile_Decorated, with a different hash on each version) and the fingerprints of Gradle's own option objects, such as javaCompiler (including its languageVersion), modularity, options, options.debugOptions and options.forkOptions.

In our runs, then, no value from the project explained the miss. The implementation line alone is enough to change the key, and the other differing lines are Gradle's own option objects, not project settings. We compared only the compile task under two Gradle versions.

What this means for an upgrade

  • Expect a cold start on the new version. In our runs the first build on a different Gradle version rebuilt, and going back to the first version restored its own entry.
  • Mixed versions meant mixed entries. For the version pairs above, a version filled and read its own entries and got no hits from the other's.
  • Java and Maven were different. In our other tests, a different Java gave separate Gradle entries (Gradle build cache hit rate low, cause 3), while switching Java did restore for Maven (Keep your Maven build cache across Java 21 and Java 27).

Our advice, not a test result: move CI and everyone who shares the cache to a new Gradle version together, and expect the first builds after the move to rebuild.

We did not test other Gradle versions, other tasks such as tests or jars, a project that uses the Gradle wrapper, other Java versions with these Gradle versions, or Linux. The Mac was busy with other jobs during the runs, so we make no claim about build times.

If nothing is restored

Work through why the hit rate is low and Gradle remote build cache not working.

Run on Gradle 9.8.0, 9.7.1 and 9.5.1 with Temurin 21.0.12.1 and FosterStack Cache 0.2.1, macOS (arm64).
