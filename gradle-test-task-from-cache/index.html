Skip tests that passed: Gradle and Maven build cache

Rerunning tests that already passed wastes build time. FosterStack Cache lets Gradle and Maven take a passing test result from the cache when nothing it depends on changed.

Does Gradle skip tests whose code didn't change?

  • In our runs, a fresh copy of the project with the same code got :test FROM-CACHE. The tests were not run.
  • In Gradle runs 3 and 4 (table below), changing the main code or the test code made the tests run again.
  • A comment added on the same line recompiled the main code, but the tests still came from the cache.
  • In our runs, a failing test ran each time. It was never taken from the cache.
  • The first run pays, the next skips. After the tests have run once for a change, a fresh copy with the same code did not run them again (run 2). With CI and laptops that is the idea, though we ran everything on one Mac.
  • In our runs, only the steps whose inputs changed ran again. Changing test code left the main code's compile step in the cache (run 4). Changing the main code left the test code's compile step in the cache (run 3).
  • An edit that does not change the compiled output can still skip the tests (run 5). The comment made Gradle compile the main code again, but the compiled output evidently did not change, because the test task found its stored result. We only tried a comment on the same line; a comment that adds lines can change the compiled output, and we did not test that.
  • A failing test was not skipped. In runs 6 and 7 the test task ran and failed each time. In run 7, a fresh copy of the same broken code ran the tests again and reported 2 tests completed, 1 failed.

We did not test tests that read the clock, the network or files outside the project. Gradle does not see those inputs, so a test result saved in the cache could be reused when it should not. That is about your tests, not about the cache.

Our advice, not a test result: if the test task does not come from the cache, work through why the hit rate is low. For a multi-module build, see Gradle build cache for a monorepo.

Does Maven skip tests that already passed?

  • In our runs, a fresh copy with the same code restored the whole build. No compile, no tests.
  • In our runs, changing the main code or the tests made Maven build the module and run the tests again.
  • In our runs, a failing test ran again each time, and a failing build was not restored.
  • The tests are skipped as part of restoring the whole module. Maven restores the module's result and then skips each step, surefire:test among them. In Gradle the test task is taken from the cache as an entry of its own; see the Gradle section above.
  • A passing build was reusable, a failing one was not. In Maven runs 5 and 6 the tests ran and failed each time. A fresh copy of the same broken code did not get a restored result.
  • Each change we made rebuilt the module and ran all its tests. Maven run 3 changed one line of main code and both tests ran again. Maven run 4 added a test and all three ran. We did not try a comment-only edit or a change to a non-source file.

We did not test a project with several modules here. For that, see Maven build cache extension in a multi-module project. We also did not test tests that read the clock, the network or files outside the project: Maven does not see those inputs, so a test result restored from the cache could stand when it should not. That is about your tests, not about the cache.

Our advice, not a test result: to run the tests every time, turn the cache off or skip the lookup for that build. The switches, and what each did in a real run, are on enable or disable the Maven build cache extension. If nothing is restored, see Maven build cache not restoring. The setup is on Maven remote build cache setup.

How we checked

Gradle. A small Java project with one class and two JUnit tests. Every run used a fresh copy of the project on the same Mac, with the same Java and Gradle, and the local build cache was switched off. The runs shared the cache server, and one Gradle home folder so the test libraries were downloaded once. A different machine or Java version was not tested. All the runs used gradle test --console=plain --no-daemon.

How much time does it save? (Gradle)

On the first project the tests are so quick that the totals were 3 seconds and 2 seconds, which tells you nothing. So we made a second project, set up the same way as above, with three more tests that each wait 10 seconds, made slow on purpose so the time is visible. It still has the two quick tests. Each build used its own copy of the project and the local build cache was off. The Mac was busy with other jobs the whole time, so all the totals are high; the gap is what matters.

Run:test taskGradle's total
1. First buildran1m 23s
2. Fresh copy, same codeFROM-CACHE35s
3. Main code changedran1m 12s
4. Fresh copy, same code againFROM-CACHE32s

The builds where the tests came from the cache finished about 40 to 50 seconds sooner: 48 seconds sooner for run 2 against run 1, and 40 seconds sooner for run 4 against run 3. (Run 3 also recompiled the main code, so it is not the same two builds as run 1.) The three sleeping tests account for at least 30 seconds of that; the rest is compiling and starting the tests, which the cached builds skipped too. Even the fully cached builds took 32 to 35 seconds on this busy Mac. Each total is a single run. Your tests will differ, so measure your own build.

Gradle files. build.gradle.kts:

plugins { java }

repositories { mavenCentral() }

dependencies {
    testImplementation(platform("org.junit:junit-bom:5.11.0"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.test { useJUnitPlatform() }

gradle.properties has one line, org.gradle.caching=true. settings.gradle.kts is the same cache setup as on enable or disable the Gradle build cache, with a different port. We used 127.0.0.1 over plain HTTP because the test ran on one machine; use HTTPS across a network.

Maven. A one-module Maven project with one class and two JUnit tests, run with the Surefire plugin (3.5.2). Every build used a fresh copy of the project on the same Mac and an empty local build cache. The builds shared the cache server, and one Maven repository folder so the test libraries were downloaded once. All runs used mvn verify, with extra options for the cache location and the shared repository. The cache setup is the one on Maven remote build cache setup.
