What does the build cache store? Gradle and Maven

Knowing what Gradle and Maven put in the cache tells you what you are paying disk for. We ran real Gradle and Maven builds against FosterStack Cache and counted every entry.

The short answer

Gradle

  • Each compileJava task stored one entry.
  • Gradle also compiled the build scripts, and those compiled scripts were stored as entries. That is why there are more entries than compile tasks. In a run where the Gradle home had already compiled the scripts, they were not stored again.
  • The jar, classes, assemble and build tasks stored nothing in our run.
  • The 13 entries from a four-module build took about 36 KB.

Maven

  • Each built module uploaded two files: its jar (about 5 KB here) and a buildinfo.xml (about 9 KB here).
  • Both of our builds also uploaded one build-cache-report.xml.
  • Our three-module build left 7 entries and 44,810 bytes on an empty server.
  • A second build that restored every module added just that one entry, the report.

What to do

We recommend that you measure your own project before you pick a limit. The server's status page (/statusz) shows the entry count and the size in bytes. To see how it changes as you build, see is my build cache server healthy, and what to alert on. To pick a size limit, see how big a server does a build cache need and how the size limit works.

Your count depends on your project: our Linux run, with slightly different build files, stored 12 entries (29,821 bytes). These are the lines Gradle printed:

Stored cache entry for task ':core:compileJava' with cache key ...
Stored cache entry for Kotlin DSL script compilation (Project/TopLevel/stage1) with cache key ...
Stored cache entry for Kotlin DSL script compilation (Project/TopLevel/stage2) with cache key ...

What was not stored

These tasks ran and stored nothing: classes, jar, assemble and build for each of the four modules. In our other runs the jar tasks never printed FROM-CACHE either. In our builds you will see them run on every fresh checkout.

See it for your own build

Start from an empty cache, run your build once with -i, and count. On our build it printed the 13 entries above:

gradle build -i | grep "Stored cache entry"

If your Gradle home has already compiled your build scripts, you will not see the script entries again: in a second run with the same Gradle home against a new empty server, only the 4 compileJava entries were stored, and the server held 4 entries and 11,425 bytes.

What a restored build adds

The second build restored all three modules and built nothing, and it uploaded one file: build-cache-report.xml. So our fully restored build still added one entry, 1,318 bytes (46,128 minus 44,810).

On the first build, against an empty server, Maven 3.10.0 also printed three [ERROR] Error downloading cache item ... buildinfo.xml lines (Maven 3.9.9 logs these misses as [INFO] Cache item not found). Those were ordinary misses on an empty cache, and the build succeeded; see enable or disable the Maven build cache extension.

What this means for sizing

In this tiny project the buildinfo.xml files were bigger than the jars: about 9 KB each against about 5 KB, and together 27,661 of the 44,810 bytes.

We tried one small project with jars of a few kilobytes. We did not test large jars, many versions of the same module, or a project with test reports.

If you do not see what you expect

Look at why the hit rate is low and enable or disable the Gradle build cache. A task that stored nothing in your build, such as the jar tasks in ours, could not come from the cache.

See Maven build cache not restoring.

Tested with FosterStack Cache 0.2.1 on macOS (arm64, Java 27), Gradle 9.8.0, Maven 3.10.0 and Build Cache Extension 1.2.3, and with 0.2.2 on a GitHub-hosted Linux machine (Java 21). The Gradle run and its log are public, and so is the Maven run.
