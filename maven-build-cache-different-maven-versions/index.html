Share your Maven build cache across Maven versions

Pin the eight plugin versions our build uses, including clean, install, deploy and site, and two machines on different Maven versions can share cache hits; leave some unpinned and, in our test, each Maven version rebuilt on its own. At FosterStack we prove everything, so here is how we proved it to ourselves: six series of real builds in both directions, and the checksums that explain it.

The short answer

  • With only some plugin versions pinned, Maven 3.10.0 and Maven 3.9.9 did not restore each other's builds, in either direction, in our two runs of each.
  • The cause was default plugin versions that differ between the two Maven versions, including clean, install, deploy and site. None of those four ran in our mvn verify builds; the log shows only resources, compiler, surefire and jar.
  • With all eight plugin versions pinned, each Maven version restored the other's build, and both computed the same checksum.

What we ran

A one-module Maven project with two JUnit tests (the one from Skip tests that already passed with the Maven build cache), with the Apache Maven Build Cache Extension 1.2.3 and a self-hosted cache (FosterStack Cache 0.2.1). We used Maven 3.10.0 and Maven 3.9.9. The 3.9.9 download was checked against the SHA-512 checksum Apache publishes. Both ran on the same Java, OpenJDK 27 from Homebrew (both jars say Build-Jdk-Spec: 27), so only Maven differed.

There were six series of three builds. The project always pinned the surefire plugin to 3.5.2. We varied how many other plugin versions we pinned:

  • Level 1: only surefire pinned.
  • Level 2: also resources 3.5.0, compiler 3.16.0 and jar 3.5.1.
  • Level 3: also clean 3.5.0, install 3.2.0, deploy 3.2.0 and site 3.22.0. That is all eight.

Each level was run twice, once with Maven 3.10.0 first and once with 3.9.9 first. Each series started on a new, empty cache server, and every build used a fresh copy of the project and an empty local build cache. All builds ran on the same Mac. Levels 1 and 2 came from one script run and Level 3 from a second one; within each script run the builds shared one local Maven repository, which a first throwaway build under each Maven version had filled with plugin files. Why they differed

We asked each Maven version for the effective POM of the Level 2 project (mvn help:effective-pom). The plugin versions that differ between the two are these defaults, none of which ran in our mvn verify builds:

PluginMaven 3.10.0Maven 3.9.9
clean3.5.03.2.0
deploy3.2.03.1.2
install3.2.03.1.2
site3.22.03.12.1

At Level 2 the resources, compiler, jar and surefire versions were the same in both, because we had pinned them. At Level 1 the stored build records show three more differences: resources 3.5.0 against 3.3.1, jar 3.5.1 against 3.4.1 and compiler 3.16.0 against 3.13.0, so seven versions differed there. Maven 3.9.9's effective POM also listed four plugins that 3.10.0's did not (antrun, assembly, dependency and release), and pinning those was not needed: the checksums matched at Level 3 without it. The build record the extension stores for each build contains the effective POM. When we compared the two Level 2 records, the only differences were the build time, the jar's hash, the checksum and the effective POM itself; the first plugin version that differs in it is clean, 3.5.0 against 3.2.0.

How to pin them

This is what we added to the Level 1 project for Level 3, inside <build><plugins> in the project's pom.xml. The surefire plugin was already pinned to 3.5.2.

<plugin><artifactId>maven-resources-plugin</artifactId><version>3.5.0</version></plugin>
<plugin><artifactId>maven-compiler-plugin</artifactId><version>3.16.0</version></plugin>
<plugin><artifactId>maven-jar-plugin</artifactId><version>3.5.1</version></plugin>
<plugin><artifactId>maven-clean-plugin</artifactId><version>3.5.0</version></plugin>
<plugin><artifactId>maven-install-plugin</artifactId><version>3.2.0</version></plugin>
<plugin><artifactId>maven-deploy-plugin</artifactId><version>3.2.0</version></plugin>
<plugin><artifactId>maven-site-plugin</artifactId><version>3.22.0</version></plugin>

The numbers are the ones we tested. Use the versions you want, as long as everyone who shares the cache uses the same ones.

What this means for a shared cache

  • Pinning all eight plugin versions made two Maven versions share one set of entries. That includes the four that did not run in our build. We did not test a build that uses other plugins.
  • Without it, two Maven versions meant two sets of entries. The server stored both and neither side got hits from the other.
  • Switching Java 21 to 27 did not matter in our other test. It did restore on one Maven version; see Keep your Maven build cache across Java 21 and Java 27.

Both Maven versions printed Java warnings about deprecated or restricted methods on Java 27, from libraries they load. The builds still succeeded. We did not test other Maven versions (3.8 or 4), other extension versions, a multi-module project, or Linux.

If nothing is restored

See Maven build cache not restoring. The setup is on Maven remote build cache setup.

Run on Maven 3.10.0 and Maven 3.9.9 with maven-build-cache-extension 1.2.3 and FosterStack Cache 0.2.1, macOS (arm64), OpenJDK 27 (Homebrew).
