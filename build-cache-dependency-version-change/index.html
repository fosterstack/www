What a dependency update rebuilds in your build cache

Know before you bump a dependency: in our runs, only the module that uses it rebuilt, in both Gradle and Maven, and going back to the old version restored the old result. At FosterStack we prove everything, so here is how we proved it to ourselves: a two-module project, five real builds per tool, one version bump and one revert.

The short answer

  • After the bump, the module that uses the dependency rebuilt. The module that does not use it came from the cache.
  • Building the new version a second time restored both modules.
  • Going back to the old version restored both modules, so the old entries were still there.
  • In our runs, Gradle and Maven gave the same pattern.

What we ran

A project with two modules. lib has no dependencies. app depends on one library, Gson (com.google.code.gson:gson), and calls it. We changed only the Gson version, from 2.10.1 to 2.11.0, and nothing else. Both series used a self-hosted cache, FosterStack Cache 0.2.1.

Gradle was 9.8.0, with the compile tasks :lib:compileJava and :app:compileJava. Maven was 3.9.9 with the Apache Maven Build Cache Extension 1.2.3 and mvn verify; all eight default plugin versions were pinned in the POM, because an unpinned plugin version changes the Maven cache key (see Maven build cache across Maven versions). Both used Java 21 (Temurin 21.0.12.1) on one Mac (arm64).

Each tool had one series of five builds. The series started on a new, empty cache server. Every build used a fresh copy of the project with no earlier build output. In Maven each build started with an empty local build cache; in Gradle the local build cache was switched off, so only the server could supply results. Gson and what it needs were downloaded once into a shared download folder before the series, so no build waited on the network. Every build ended with BUILD SUCCESSFUL (Gradle) or BUILD SUCCESS (Maven).

In the Gradle columns, "ran" means the task line (for example > Task :app:compileJava) had nothing after it and "from cache" means FROM-CACHE. In the Maven columns, "restored" means Maven printed Found cached build, restoring for that module and "built" means it did not.

What this means when you update a dependency

  • The cost is the modules that use it. In our runs a module with no use of the library was not rebuilt, in either tool.
  • You can try a version and go back. After the bump, going back to the old version restored both modules, so the old results were still available.
  • The server kept the new result. Build 4 restored both modules from it. We ran one machine, one after another, so we did not test several people or CI against developers.

Our advice, not a test result: bump a version in one change, let one build fill the cache, and then expect later builds to restore.

We did not test a dependency that lib and app both use, a module that depends on app (a module downstream of the change), other libraries, other versions, the Gradle wrapper script (gradlew), or Linux. The runs lasted under a minute against a server with no size limit; on a busy server with a limit, old entries can be removed. The Mac was busy with other jobs during the runs, so we make no claim about build times.

If nothing is restored

Work through why the Gradle hit rate is low or Maven build cache extension not restoring.

Run on Gradle 9.8.0 and Maven 3.9.9 (Build Cache Extension 1.2.3), Temurin 21.0.12.1, FosterStack Cache 0.2.1, macOS (arm64).
