Which modules rebuild when you change one? Gradle vs Maven

Know before you refactor a shared module: in our runs Gradle rebuilt a downstream module only when the public API of the module it uses changed, while Maven's build cache extension rebuilt every downstream module after any change, even a comment. At FosterStack we prove everything, so here is how we proved it to ourselves: a three-module chain, four kinds of change, and a new empty cache server for each.

The short answer

  • Gradle: a body-only or comment-only change in the bottom module rebuilt only that module. The two modules above it came from the cache. A change to its public API rebuilt the module directly above it too, but not the top one.
  • Maven: any change in the bottom module, a method body, a comment or a new method, rebuilt all three modules.
  • Both: a change in the top module alone rebuilt only the top module. The two below it were restored.

What we ran

A project with three modules in a chain: core, then service (which uses core), then app (which uses service). Each has one small Java class. In Gradle each module used the other with implementation(project(...)). In Maven each used the other as an ordinary dependency. There are no outside libraries.

For each of four changes we started a new, empty cache server (FosterStack Cache 0.2.1) and ran two builds. Build 1 was the unchanged project, which filled the server. Build 2 was the same project with one change. Every build used a freshly written copy of the project and an empty local build cache (Gradle: local cache switched off, with a new empty Gradle home). Every build ended with BUILD SUCCESSFUL (Gradle) or BUILD SUCCESS (Maven). All of it ran on one Mac.

  • Body: a number returned by a method in core changed.
  • Comment: one comment line added in core.
  • API: a new public method added to core.
  • App only: a number changed in app.

Gradle ran the three compileJava tasks (Gradle 9.8.0). Maven ran mvn verify (Maven 3.9.9, Build Cache Extension 1.2.3, all eight default plugin versions pinned, see Maven build cache across Maven versions). Both used Java 21 (Temurin 21.0.12.1). Maven ran a fuller build than Gradle did, so compare the pattern, not the amount of work.

Every build 1 built all three modules, as expected on an empty server. In the Gradle column "ran" means the compileJava task line had nothing after it and "from cache" means FROM-CACHE. In the Maven column "restored" means Maven printed Found cached build, restoring for that module.

Why they differ

This part is what the logs show, plus the usual explanation.

  • Maven: to work out a module's cache key, the extension also works out the key of each module it depends on, and uses it. The Maven log shows this: when it calculates service it calculates core first. In the comment run, core had a new key and so did service (efd19a4c19b933af before, 3d90eee1e1f99534 after). So a change below changes every key above it.
  • Gradle: Gradle compiles a module against the public API of the modules it uses, not against their compiled code. A body or comment change leaves that API as it was, so the compile of service found the entry it needed. Adding a public method changed the API, so service ran. app uses service, whose own API did not change, so it came from the cache. We checked results, not Gradle's internals.

What this means for a refactor

  • In Maven, a shared bottom module touches every build above it. In our runs even a comment in it cost a rebuild of the whole chain.
  • In Gradle, the change that costs is a change to what the module shows to others. Edits inside method bodies stayed inside the module in our runs.
  • Both tools handled the top of the chain well. A change in app rebuilt only app.

Our advice, not a test result: in Maven, keep very widely shared modules small and rarely edited, so a change there is rare.

We did not test: Gradle's api dependencies (we used implementation only), tests or jar tasks in Gradle, annotation processors, Kotlin, a change in the middle module, other Gradle or Maven versions, bigger projects, or Linux. The Mac was busy with other jobs during the runs, so we make no claim about build times.

If nothing is restored

Work through why the Gradle hit rate is low or Maven build cache extension not restoring, and see Maven Build Cache Extension in a Multi-Module Project.

Run on Gradle 9.8.0 and Maven 3.9.9 (Build Cache Extension 1.2.3), Temurin 21.0.12.1, FosterStack Cache 0.2.1, macOS (arm64).
