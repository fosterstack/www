Which modules rebuild when you change one? Gradle vs Maven

Know before you refactor a shared module: in our runs Gradle recompiled the module above only when we added a public method to the module below, while Maven's build cache extension rebuilt all three modules after each of our three changes to the bottom one, even a comment. At FosterStack we prove everything, so here is how we proved it to ourselves: a three-module chain, four kinds of change, and a new empty cache server for each.

The short answer

  • Gradle (compile tasks): a body-only or comment-only change in the bottom module recompiled only that module. The two modules above it came from the cache. Adding a public method recompiled the module directly above it too, but not the top one.
  • Maven: each of our three changes in the bottom module (a method body, a comment, a new method) rebuilt all three modules.
  • Both: in the one run each, a change in the top module alone recompiled (Gradle) or rebuilt (Maven) only the top module. The two below it came from the cache.

What we ran

A project with three modules in a chain: core, then service (which uses core), then app (which uses service). Each has one small Java class. In Gradle each module used the one below it with implementation(project(...)). In Maven each used the one below it as an ordinary dependency, with the compiler set to Java release 17. There are no outside libraries.

For each of four changes we started a new, empty cache server (FosterStack Cache 0.2.1) and ran two builds. Build 1 was the unchanged project, which filled the server. Build 2 was the same project with one change. Every build used a freshly written copy of the project. The local build cache was empty (Maven) or switched off (Gradle, with a new empty Gradle home). Maven's plugins were downloaded once into a shared folder by a throwaway build before the runs. Every build ended with BUILD SUCCESSFUL (Gradle) or BUILD SUCCESS (Maven). All of it ran on one Mac.

  • Body: a number returned by a method in core changed.
  • Comment: one comment line added in core.
  • API: a new public method added to core.
  • App only: a number changed in app.

Gradle ran the three compileJava tasks (Gradle 9.8.0). Maven ran mvn verify (Maven 3.9.9, Build Cache Extension 1.2.3, all eight default plugin versions pinned, see Maven build cache across Maven versions). Both used Java 21 (Temurin 21.0.12.1; Maven compiled with release 17). Maven ran a fuller build than Gradle did, and Gradle ran only the compile tasks, so the Gradle column says nothing about tests or jars (we did not run them). Maven's verify had no tests to run here.

Why Maven rebuilds more than Gradle

This part is what the logs show, plus the usual explanation.

  • Maven: the log shows that while it works out the key for service it also works out the key for core. In the comment run, core had a new key and so did service (efd19a4c19b933af before, 3d90eee1e1f99534 after), though no file in service changed. That is consistent with a module's key including the keys of the modules it depends on.
  • Gradle: Gradle's documentation describes the cache key for compiling a module as looking only at the public API of the compiled classes it uses; method bodies, private parts and comments are left out. Our results are consistent with that: a body or comment change left service and app in the cache, and a new public method made service run while app (which uses service, whose own public API did not change) still came from the cache. We checked results, not Gradle's internals.

Gradle compile avoidance vs Maven: what it means for a refactor

  • In our Maven runs, every change to the bottom module rebuilt every module above it. Even a comment cost a rebuild of the whole chain.
  • In our Gradle compile runs, the change that cost more was a change to what the module shows to others. Edits inside method bodies stayed inside the module.
  • In both tools, a change in app recompiled (Gradle) or rebuilt (Maven) only app. That was one run each.

Our advice, not a test result: in Maven, expect an edit to a widely shared module to rebuild everything above it, and batch such edits.

We did not test: Gradle's api dependencies (we used implementation only), tests or jar tasks in Gradle, annotation processors, Kotlin, a change to a public constant's value, a change in the middle module, other Gradle or Maven versions, bigger projects, or Linux. The Mac was busy with other jobs during the runs, so we make no claim about build times.

If nothing is restored

Work through why the Gradle hit rate is low or Maven build cache extension not restoring, and see Maven Build Cache Extension in a Multi-Module Project.

Run on Gradle 9.8.0 and Maven 3.9.9 (Build Cache Extension 1.2.3), Temurin 21.0.12.1, FosterStack Cache 0.2.1, macOS (arm64).
