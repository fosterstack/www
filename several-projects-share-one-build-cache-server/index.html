Can several projects share one build cache server?

Yes, several projects can use one FosterStack Cache server. In our runs they shared the results of identical work and could read each other's results. If a group must not see another group's results, give that group its own server.

The short answer

  • Different code did not clash in our runs. Project B's own compile found nothing stored, so it ran and stored its own entry next to project A's.
  • Identical work is shared. A copy of project A in another folder restored A's compile result. Project B also restored one entry from A: the compiled build script. Both build files contain the same text, so the result is the same. That reuse is harmless.
  • One login reaches every project, which is a warning, not a feature. The login that B's builds used also fetched A's entry, so anyone with it sees every project's results. The read-only login read both, and its write got a 403.
  • One size cap covers every project. With a small cap, B's store pushed out A's entry, and a copy of A pushed B's out again.
  • Separate servers kept teams apart in our runs. Team 2's server restored nothing from team 1's. Each team's login got a 401 on the other server.

What to do

Our advice, not a test result:

  • One server is fine when everyone may see everyone's results. Many repos in one company often fit. Two repos that build the same thing can reuse each other's results.
  • Use one server for each group that must not read another group's results. Each server has its own data folder and logins.
  • Treat everything in the cache as readable by anyone with a login. Do not rely on a project name to hide it.
  • Give CI the read-write login and everyone else the read-only one. See let CI write and developers read and can someone poison our shared build cache.
  • Size the cap for all projects together. See how big a server a build cache needs and how the size limit works.

Gradle and Maven builds can use the same server too. See one build cache server for Gradle and Maven.

How we checked

FosterStack Cache 0.2.1 and Gradle 9.8.0 with Java 21 on a Mac (arm64), one machine. Project A has three classes, project B has four different ones, and project C is an exact copy of A in a different folder. Each build ran compileJava and jar with a new Gradle home, Gradle's --no-daemon flag and the local build cache off. The cache address and login reached the build only as environment variables. All logins were made up for the test. Each row is one run.

One server, no size cap. The same read-write login for all three builds.

Limits: Gradle only, three small projects, one run of each case. We did not test Maven, many projects building at once, or real project sizes.
