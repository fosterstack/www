Can I Restart the Cache Server While Builds Run?

Yes. In our runs, a build that was already running finished normally when we stopped and restarted FosterStack Cache. At worst it printed one warning and stopped using the cache for the rest of that build.

The short answer

  • A short restart is often invisible. When the server was back within 2 seconds and the build did not touch the cache in that moment, there was no warning.
  • If the build did touch the cache while the server was down, Gradle printed one warning and switched the remote cache off for the rest of that build. The build still ended with BUILD SUCCESSFUL.
  • The next build used the cache again and rebuilt only what had not been stored.
  • A normal stop waits for an upload that is in progress, but only for 10 seconds. A kill loses the upload in progress.

What to do

Our advice, not a test result:

  • Stop the server with a normal stop, not a kill. docker stop sends one first. Our runs started the server binary directly, not in Docker.
  • Restart in a quiet moment. The server was back in well under a second in our runs, so a quiet moment keeps the chance of a warning small.
  • Do not worry about one warning. The lines to expect are Could not store entry or Could not load entry, then The remote build cache was disabled during the build due to errors. The next build stores what was missed.
  • Keep the same data folder or volume. That is what keeps the stored results. See does the build cache survive a restart.
  • For an upgrade, pull the new version first, then stop and start, so the gap is only the restart. What happens to the data across releases is on upgrade a build cache server.
  • Check that the server answers before you send builds back. The /healthz address returns 200 when it is up. See monitor the build cache.

If the server is down for a whole build, nothing breaks either. That case is on what happens when the cache server is down.

How we checked

FosterStack Cache 0.2.1 on a Mac (arm64), no password. Gradle 9.8.0, Java 21, one fresh copy of the project per build, no daemon, the local build cache off. Compile tasks finish too fast to catch a restart, so each of the four modules had a cacheable task that sleeps for 8 seconds. We sent the signal to the server's process ID and started it again on the same data folder. All builds ended with BUILD SUCCESSFUL. Each row is one run; we did not repeat them.

We also started a build while the server was stopped. It printed one Could not load entry warning, then built all four modules locally. After we started the server, the next build built and stored all four. The one after that took all four from the cache.

How long the server was unreachable. We stopped and started it five times in a row for each case, and polled /healthz until it answered. This measures the restart on a busy laptop, not a promise for your server.

After a kill, the server logs unclean shutdown detected, reconciling stores before serving and checks its files before it answers. No entries were lost in these runs.

An upload in progress when the server stops. Gradle's uploads finish too quickly to catch, so we used curl to send a large file slowly (2 MB per second) and stopped the server 3 seconds in.

UploadStopWhat happenedEntry afterwards
20 MBNormal stopThe server waited, the upload finished with 201, the server exited cleanly after 7.4 secondsReadable

An entry that was stored earlier stayed readable in every case. We did not test whether a later start removes the temporary file left by the 40 MB case.

Not tested: Docker, Kubernetes or Compose rollouts, Maven builds, other releases, and more than one build running at once.
