We upgraded Gradle or Maven and builds got slow

After you upgrade Gradle or Maven, the first builds on the new version can rebuild instead of restoring from the cache. FosterStack Cache keeps the results of both versions, so the new version fills its own entries and the old ones are still there if you go back.

What to do

  • Upgrade CI and every laptop that shares the cache at the same time. Then the first builds fill the cache for everyone.
  • Expect the first builds on the new version to rebuild. They store their results for the builds after them.
  • In Maven, pin all eight plugin versions in your pom.xml. Then two Maven versions can share cache entries. The list is below.

For Gradle, all we can say is what we saw: in our three pairs of Gradle versions, each version used its own entries.

Pin the Maven plugin versions

Put these inside <build><plugins>. These are the versions we tested. Use the ones you want, as long as everyone who shares the cache uses the same ones.

<plugin><artifactId>maven-resources-plugin</artifactId><version>3.5.0</version></plugin>
<plugin><artifactId>maven-compiler-plugin</artifactId><version>3.16.0</version></plugin>
<plugin><artifactId>maven-jar-plugin</artifactId><version>3.5.1</version></plugin>
<plugin><artifactId>maven-clean-plugin</artifactId><version>3.5.0</version></plugin>
<plugin><artifactId>maven-install-plugin</artifactId><version>3.2.0</version></plugin>
<plugin><artifactId>maven-deploy-plugin</artifactId><version>3.2.0</version></plugin>
<plugin><artifactId>maven-site-plugin</artifactId><version>3.22.0</version></plugin>
<plugin><artifactId>maven-surefire-plugin</artifactId><version>3.5.2</version></plugin>

Why it happens

  • Gradle: the cache key includes Gradle's own compile task. A different Gradle version gives a different key. In our runs the values from the project were identical, and the lines that differed described Gradle's own task and compiler objects.
  • Maven: Maven fills in a default version for each plugin you did not pin, and those defaults differ between Maven versions. They end up in the cache key. In our runs the differing defaults included clean, install, deploy and site.

If the cache is still cold after you match versions, see why the Gradle hit rate is low or why the Maven cache is not restoring. The Maven setup is on Maven remote build cache setup.

In all nine series, going back to the first version restored its own entry. One build per cell, a new empty cache server per series, a fresh project copy for every build. Gradle: a four-module project, the :core:compileJava task, Temurin 21.0.12.1. Maven: one module with two tests, mvn verify, Build Cache Extension 1.2.3, OpenJDK 27. FosterStack Cache 0.2.1 on a Mac (arm64). Not tested: other versions, Gradle test or jar tasks, a multi-module Maven build, Linux.
